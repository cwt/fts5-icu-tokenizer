# Bug 9 — Tokenizer name passed as locale override

**File:** `src/fts5_icu.zig` (`icuCreate`)
**Severity:** MEDIUM

## Description

FTS5's `xCreate` receives the **tokenizer name** as `azArg[0]`
(e.g. `"icu_ja"`), but the callback treated it as a locale override:

```zig
if (nArg > 0 and azArg != null and azArg[0] != null and azArg[0][0] != 0) {
    locale = std.mem.span(azArg[0]); // "icu_ja" OVERWRITES "ja"!
}
```

So `tokenize='icu_ja'` set locale `"icu_ja"`: wrong rules
(`ICU_RULE_DEFAULT` instead of `ICU_RULE_JA`) and an invalid ICU locale
for `ubrk_open` (silent root fallback → CJK split per-character). Tests
missed it because character-by-character tokenization still satisfies
phrase queries. All eight locale libraries were affected.

## Impact

- Wrong word boundaries and wrong transliteration chains for every
  locale-specific deployment; silently degraded search quality.

## Fix

The baked-in `build_options.locale` is already correct; only a **second**
argument overrides it, matching SQLite's own `fts5_icu.c`:

```zig
if (nArg > 1 and azArg != null and azArg[1] != null and azArg[1][0] != 0) {
    locale = std.mem.span(azArg[1]);
}
```

Guarded by the `icuCreate ignores tokenizer name` unit test.

**Status:** ✅ FIXED — 23310bf6.
