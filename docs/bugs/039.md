# Bug 39 — CacheMutex spinlock contention and fallible Thread.yield

**File:** `src/tokenizer.zig` (`CacheMutex`, ~17–35)
**Severity:** LOW (concurrency / cache contention)

## Description

`CacheMutex.lock` currently spins with `cmpxchgStrong` on every iteration and propagates errors from `std.Thread.yield()`:

```zig
fn lock(m: *CacheMutex) !void {
    var spins: usize = 0;
    while (m.state.cmpxchgStrong(0, 1, .acquire, .monotonic) != null) {
        if (spins < 1000) {
            std.atomic.spinLoopHint();
            spins += 1;
        } else {
            try std.Thread.yield();
        }
    }
}
```

1. **Cache-line bouncing:** `cmpxchgStrong` issues an atomic read-modify-write (exclusive cache-line acquisition) on every spin iteration, invalidating the cache line across cores while a writer holds the lock. Using `cmpxchgWeak` (or spinning on `m.state.load(.monotonic) != 0` before attempting `cmpxchgWeak`) avoids MESI cache-coherency storms under multi-threaded contention.
2. **Unnecessary error union:** If `std.Thread.yield()` returns an error (`error.SystemCannotYield`), propagating it aborts `tokenizeText` with `c.SQLITE_ERROR`. Falling back to `std.atomic.spinLoopHint()` (`std.Thread.yield() catch std.atomic.spinLoopHint()`) makes `lock(m: *CacheMutex) void` infallible.

## Impact

- Unnecessary cache-line contention under high multi-threaded override load, and an avoidable failure path if OS yield fails.

## Suggested fix

Use `cmpxchgWeak` with a relaxed load check and handle `std.Thread.yield()` fallback internally so `lock` returns `void`.

**Status:** OPEN.
