# Bug 29 — Single-retry overflow handling; silent drop on second overflow

**File:** `src/tokenizer.zig`
**Severity:** LOW (robustness)

## Description

Both transliteration growth sites (`transliterateString` retry and the
pre-translit retry in `tokenizeText`) attempt exactly one
grow-and-retry using ICU's reported length. Correct under ICU's overflow
contract, but: if the second attempt also overflows, the pre-translit path
returns `SQLITE_ERROR` (whole document lost), and if the per-token
`u_strToUTF8WithSub` conversion overflows its grown buffer, the token is
silently skipped (the `!U_FAILURE and utf8_len > 0` gate just doesn't
fire).

## Impact

- Theoretical today (ICU reports exact needs), but a single retry is one
  contract misunderstanding away from data loss with no diagnostic.

## Suggested fix

Grow in a `while (status == U_BUFFER_OVERFLOW_ERROR)` loop with a small
retry cap; on persistent overflow return an error (never silently skip).
Regression test: force a double-overflow via a shrinking mock or an
expanding custom rule chain.

## Implemented

All three sites use a bounded `while` loop (`max_translit_retries = 8`):
`transliterateString` and the pre-translit retry keep their existing loud
`U_FAILURE` checks for exhaustion, and the per-token UTF-8 stage now
returns `SQLITE_ERROR` on persistent failure instead of silently skipping
the token. No new deterministic test is possible — ICU always reports the
exact need, so a second overflow is unreachable by construction; the
existing Any-Name overflow test and the token-preservation test exercise
the loop body, and the full suite confirms unchanged success-path
behavior.

**Status:** ✅ FIXED.
