# Bug 31 — Position-map safety rests entirely on phantom math

**File:** `src/tokenizer.zig` (`fillSegment`, anchor loop, offset mapping)
**Severity:** LOW (hardening)

## Description

The end-pairing analysis for [Bug 19](019.md) shows `seg_orig_start <=
utf16_pos` always holds today, so `oe - os` in `fillSegment` cannot
underflow and `byte_offset_map` reads (only `[0..utf16_pos]` are ever
written) stay initialized. But nothing enforces this: a future rule change
adding another whitespace-producing mapping could produce `os > oe`, which
underflows `usize` (Debug panic / ReleaseFast wrap) and yields
`utf16_pos + 1` map values that read **uninitialized** stack/heap slots.

## Impact

- No live defect; a latent memory-safety tripwire for future rule edits.

## Suggested fix

One defensive clamp in `fillSegment` (`if (os > oe) pin to oe`) plus a
debug assertion that every emitted `position_map` value satisfies `<=
utf16_pos`. Zero cost on the hot path.

**Status:** OPEN.
