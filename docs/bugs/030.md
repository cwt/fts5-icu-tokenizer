# Bug 30 — Missing null checks on FTS5/extension pointers

**File:** `src/fts5_icu.zig`
**Severity:** LOW (hardening)

## Description

- `icuCreate` dereferences `ppOut.*` without checking `ppOut` for null.
- `initExtensionForLocaleInner` dereferences `pzErrMsg.*` on every error
  path (also reachable via `entrypointType.init`, which forwards it
  unchecked).
- `api.xCreateTokenizer_v2.?` / `api.xCreateTokenizer.?` are force-unwrapped
  (the `iVersion < 3` guard covers the v2 case, but a null v1 pointer would
  still segfault).

SQLite's contract almost certainly guarantees all of these, so this is
defense-in-depth, not a live crash.

## Impact

- A hostile or mocked caller (or a future SQLite behavior change) turns
  these into segfaults instead of clean `SQLITE_ERROR`/`SQLITE_NOMEM`
  returns.

## Suggested fix

One `if` each: `ppOut orelse return SQLITE_ERROR`, guard `pzErrMsg`
before writing, and `orelse return SQLITE_ERROR` on the register function
pointers.

## Implemented

`icuCreate` rejects a null `ppOut` before allocating (leak-free);
`pzErrMsg` writes are null-guarded on all three error paths; the
`xCreateTokenizer(_v2)` calls unwrap to `SQLITE_ERROR` instead of
force-unwrapping. Guarded by a null-`ppOut` rejection test (the
`pzErrMsg`/register paths need a live `sqlite3_api_routines` table and are
not unit-testable in-process).

**Status:** ✅ FIXED.
