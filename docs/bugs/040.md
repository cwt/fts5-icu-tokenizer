# Bug 40 — Double UTF-8 decode pass and duplicated decoder in tokenizeText

**File:** `src/tokenizer.zig` (`buildByteOffsetMap` ~242–256, `convertUtf8ToUtf16Tolerant` ~262–291, `tokenizeText` ~446–455)
**Severity:** MEDIUM (unoptimized algorithm & code duplication)

## Description

In `tokenizeText`, every valid UTF-8 input is decoded **twice** from start to finish:

```zig
if (std.unicode.utf8ToUtf16Le(utf16_text_buffer, text)) |n| {
    utf16_pos = n;
    buildByteOffsetMap(byte_offset_map, text);
} else |_| {
    utf16_pos = convertUtf8ToUtf16Tolerant(utf16_text_buffer, byte_offset_map, text);
}
```

1. **Redundant full-string pass:** `std.unicode.utf8ToUtf16Le` walks all of `text` decoding UTF-8 into `utf16_text_buffer`. Immediately afterwards, `buildByteOffsetMap` walks all of `text` a second time, calling `utf8ByteSequenceLength` and `utf8Decode` on every character solely to populate `byte_offset_map`.
2. **Duplicated decoding logic:** `buildByteOffsetMap` and `convertUtf8ToUtf16Tolerant` implement the exact same tolerant UTF-8 state walk (`utf8ByteSequenceLength` + `utf8Decode` + `U+FFFD` substitution + surrogate pair offset assignment).
3. `convertUtf8ToUtf16Tolerant` produces byte-identical UTF-16 output and `byte_offset_map` entries to `utf8ToUtf16Le` + `buildByteOffsetMap` on all valid UTF-8 while also handling malformed UTF-8 in a single pass.

## Impact

- Doubles the UTF-8 decoding work on the hot path for every valid document and query, while maintaining two copies of the same decoding loop (noted as a remaining item from [Bug 34](034.md)).

## Suggested fix

Unify UTF-8 to UTF-16 conversion and `byte_offset_map` construction into a single pass (with an ASCII fast-path chunk loop for pure-ASCII runs) and remove the redundant `buildByteOffsetMap` function.

## Implemented

Removed `buildByteOffsetMap` and the std-converter-then-redecode flow in `tokenizeText`. `convertUtf8ToUtf16Tolerant` is now the single converter: it fills the UTF-16 buffer and the byte-offset map in ONE pass, with an ASCII-run fast path (1 byte -> 1 unit, no per-character decoding), and never writes past either output buffer. For valid UTF-8 its output is identical to `std.unicode.utf8ToUtf16Le` plus the old offset map; malformed-input behavior is preserved (lone invalid byte keeps its byte value, as `tests/test_malformed_utf8.sql` relies on).

While consolidating, a latent crash in the old fallback decoder was fixed: a multi-byte sequence truncated by the end of the text (e.g. `"x\xE2\x82"`) passed a too-short slice to `std.unicode.utf8Decode`, whose `utf8Decode2/3/4` assert on the lead byte (panic in Debug/ReleaseSafe, undefined behavior in ReleaseFast). It is now substituted with U+FFFD.

Tests: a differential test (`convertUtf8ToUtf16Tolerant matches std converter and offset map on valid UTF-8`) compares the converter against `std.unicode.utf8ToUtf16Le` and an independent codepoint-walk offset oracle over ASCII, CJK, mixed-script, astral and >512-byte inputs; `...tolerates malformed input and keeps offsets` covers invalid/truncated sequences; `...never writes past either output` covers undersized buffers. The SQL integration (`tests/test_malformed_utf8.sql`, `scripts/test.sh`) was also re-run and is unchanged.

Verified with `zig build test` on both Zig 0.16.0 and Zig 0.17.0.

**Status:** ✅ FIXED.
