# Bug 27 — Unchecked @intCast on untrusted FTS5 text lengths

**File:** `src/tokenizer.zig`
**Severity:** MEDIUM (robustness / safety)

## Description

`text.len`-derived `usize` values are cast to `i32` with no bounds checks
at ~10 sites (`transliterateString`: limit/out_len/capacity/need;
pre-translit: `tlimit`/`tlen`/capacity; token loop: `norm_len`,
`byte_offset_map` indices, `iStartByte`/`iEndByte` as `c_int`), plus
`i32 → usize` casts on ICU-reported lengths. This violates the Zig 0.16
rule to bounds-check before `@intCast` on external data. Shipped libraries
build `ReleaseFast`, where out-of-range `@intCast` silently wraps **and**
slice bounds checks are compiled out — a ~700MB+ document (legal for
SQLite; `req_norm_cap = utf16 * 3 + 64` overflows `i32` first) degrades
from "panics in test" to wrong offsets / potential OOB access.

## Impact

- Extreme-size documents (hundreds of MB) can produce silently wrong FTS5
  offsets instead of an error; worst case is memory-unsafe in ReleaseFast.

## Suggested fix

One entry guard per function (e.g. `if (text.len > MAX_TEXT) return
SQLITE_ERROR` / `error.TextTooLarge`) sized so every downstream
`@intCast` to `i32` is provably in range. Add a regression test with an
oversized input asserting the error path, run under the Debug test module
([Bug 25](025.md)).

**Status:** OPEN.
